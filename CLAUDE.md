# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A token-efficient, multi-stage email ingestion and triage pipeline. It concurrently pulls unread mail from Gmail (API) and IMAP (Zoho), filters noise for free, classifies the rest with a cheap LLM, and escalates only high-priority items to a premium LLM for executive summaries. Results are cached in SQLite so repeated runs cost zero tokens/network calls for already-seen messages. It's exposed both as a CLI (`main.py` / `email-triage.sh`) and as an MCP server (`mcp_server.py`) for AI agents/editors, with a Vite/React dashboard SPA (`web/`) for humans.

A DB-backed multi-user model (`data/app.db`: users/sessions/mcp_tokens/integrations/settings) coexists with the original filesystem-profile model — new users log in with a real password and can connect multiple Gmail/Zoho/IMAP accounts each, while any profile not yet run through `migrate_to_db.py` keeps working exactly as before on the legacy filesystem-only path. See "Multi-tenant profiles → DB-backed users" below before touching anything auth- or profile-related.

## Architecture

### Tiered triage pipeline (`triage.py` — `EmailTriageEngine`)

Every unread email is evaluated in escalating order until a level is decided; each stage after Level 0 costs more tokens/latency, so cheaper checks always run first:

1. **VIP bypass**: sender matches `triage.whitelist_vip_senders` → skip straight to Level 2 (full body fetch + premium summary).
2. **Level 0 (static, free)**: regex/substring match against `triage.blacklist_keywords` / `blacklist_senders`, unless the sender's domain is in `whitelist_domains`. Hit → tag `"low"`, level 0.
3. **Level 0.5 (reranker semantic router, optional)**: if `triage.tei_router_enabled`, the email is reranked (via a Cohere/Jina-style `/rerank` endpoint at `triage.tei_url`, using `triage.tei_model`/`triage.tei_api_key`) against two fixed anchor documents ("important" vs "noise", `RERANK_IMPORTANT_ANCHOR`/`RERANK_NOISE_ANCHOR` in `triage.py`). The higher-scoring anchor's relevance score is compared against `tei_noise_threshold` / `tei_signal_threshold` to short-circuit straight to noise (level 0) or straight to summarization (level 2); ambiguous results fall through to Level 1. This stage still goes by "TEI" in code/config for historical reasons, but the actual backend is a reranker, not a TEI sequence-classifier — the request/response shape is `{"model", "query", "documents"}` → `{"results": [{"index", "relevance_score"}, ...]}`, not TEI's older `{"inputs"}` → `[{"label", "score"}, ...]`.
4. **Level 1 (cheap LLM ternary classification)**: sends From/Subject/Snippet only (no body fetch) to `settings.triage_model` via an OpenAI-compatible `/chat/completions` proxy, expecting strict JSON (`TriageDecision` Pydantic model: `suggested_level` 0/1/2, `reason`, `confidence_score`, `tag`). `triage.triage_type` can be `"llm"` or `"tei"` (routes to the same rerank-based classifier instead of an LLM call, via `EmailTriageEngine._rerank`).
5. **Ambiguity escalation**: if Level 1's `confidence_score` is below `triage.confidence_threshold`, the full body is fetched and re-evaluated by the *premium* model (`run_level_1_premium_escalation`) using the same schema — this is a safety net, not a normal path.
6. **Level 2 (premium summarization)**: only for level-2 items. Full body is fetched, sent to `settings.summary_model`, expecting `SummaryResult` JSON (`summary`, `confidence_score`, `tag`).

This exact sequence is duplicated in two places that must stay in sync when changed: `main.py::process_account_emails` (CLI) and `mcp_server.py::_run_tiered_triage` (the MCP server's background sync engine — see below), plus `auto_rater_runner.py::run_config` (benchmark harness). There is no single shared "run one email through the pipeline" function — the tiering logic is duplicated in each of these, with `EmailTriageEngine` only providing the individual stage primitives (`run_level_0_static`, `run_tei_router`, `run_level_1_classification`, `run_level_1_premium_escalation`, `run_level_2_summarization`, `is_vip_sender`). Unlike `main.py`'s version, `mcp_server.py::_run_tiered_triage` always receives an already-downloaded `full_body` rather than lazily fetching it mid-pipeline, since the MCP server's sync engine downloads full content for every unread message upfront (see "Background sync scheduler" below).

System prompts for the LLM stages are resolved with the same DB-over-legacy precedence as everything else in the DB-backed world: `data/app.db` (`prompts_store.py`, admin-editable at `/admin/prompts`) → `prompts.yml` (keys `level_1_fast_triage`, `level_1_premium_escalation`, `level_2_summarization`) if present → hardcoded defaults in `prompts_store.DEFAULT_PROMPTS` (the single source of truth `triage.py`'s three `run_level_*` methods fall back to, rather than duplicating the text inline). `EmailTriageEngine.__init__` loads `prompts.yml` first, then overlays any DB rows on top — a no-op until `data/app.db` exists and has been seeded. Seeding (`prompts_store.seed_from_yaml_or_defaults`) runs automatically and idempotently at every SSE-transport startup, alongside `appdb.init_app_db()`/`seed_admin()`: any prompt key not already in the DB is copied in from `prompts.yml` (or the hardcoded default if `prompts.yml` doesn't define it), while a key an admin has already customized is never touched. Prompts are process-wide (like LLM model choice), not per-user — one edit in the admin UI changes every user's pipeline.

### Real cache layer (`db.py` — `EmailDB`, SQLite at `<profile>/email_cache.db`)

Every processed message is keyed by RFC `Message-ID` in the `email_cache` table (triage level, tag, reason, score, summary, per-stage token/duration metrics, TEI telemetry, plus download-tracking columns `snippet`/`is_unread`/`source_id`/`downloaded_at`/`display_count` — the last incremented by `fetch_and_process_unread` each time a triaged row is actually rendered, and read back by auto-mark-read). On subsequent runs, `get_cached_result(message_id)` reconstructs the full result dict at zero network/token cost — this is why re-running the CLI repeatedly is cheap. `token_logs` tracks per-call token spend for auditing. New columns are added via best-effort `ALTER TABLE` in `_init_db` (append-only migration pattern — no down-migrations).

A row can now exist in `email_cache` *before* triage has run: `upsert_email_metadata(...)` is the download-phase write (populates `email_body`/`snippet`/`is_unread`/`source_id` without touching triage columns), while `save_triage_result(...)` is the triage-phase write. Both use `INSERT ... ON CONFLICT(message_id) DO UPDATE` rather than a destructive replace, with `email_body` specifically protected via `COALESCE(excluded.email_body, email_cache.email_body)` so a triage-phase write that passes `email_body=None` (e.g. the Level-0/TEI-noise branches, which never need a body) doesn't null out content the download phase already fetched. Because of this, "row exists" no longer means "already triaged" — `is_processed(message_id)` and any cache-skip check must test `triage_level IS NOT NULL`, not just row presence.

`sync_state` (`account TEXT PRIMARY KEY, checkpoint_val TEXT`) is used as a generic per-account JSON blob store via `save_sync_summary`/`get_sync_summary`, holding each account's last-download timestamp/counts/errors for the `get_last_download_time` MCP tool.

Two more additive columns, `integration_id`/`provider`, exist for the DB-backed multi-account world (see below) — `account` (the string, e.g. an email address) remains the primary key every existing query filters on; these two are populated going forward once a mailbox is backed by a `data/app.db` `integrations` row, and backfilled for pre-existing rows by `migrate_to_db.py` (`EmailDB.backfill_integration`).

### Multi-tenant profiles → DB-backed users (`config.py`, `appdb.py`, `migrate_to_db.py`)

**This is a hybrid, in-progress architecture** — a DB-backed multi-user model has been built alongside the original filesystem-based profile model, and the two coexist by design until `migrate_to_db.py` is actually run against a given deployment's `profiles/` directory (which has **not** been done for this repo's real `profiles/jenny`/`profiles/stone` yet — that's a deliberate, separate operator action). Every new code path resolves a profile/user by first checking `data/app.db` for a matching user, and falls back to the original filesystem-only construction when no such user exists. This means: **do not delete the legacy machinery** (`config.py::_load_for_profile_legacy`, `mcp_server.py`'s `_PLACEHOLDER_GMAIL_ACCOUNT`/`_PLACEHOLDER_IMAP_LOGIN`/`_is_configured`, `generate_profile_token.py`, `load_token_profile_map`) until every real profile has actually been migrated — it's the only thing keeping unmigrated profiles working.

**Legacy path (unchanged, still the default until migrated):** DB path, Gmail token/credentials, `.env` scoped under `profiles/<name>/`, created on demand. Config resolution order (later overrides earlier): global `data/config.yml` → `profiles/config-local.yml` → `profiles/<name>/config.yml` → `profiles/<name>/config-local.yml`. Within `load_from_yaml`, a YAML value is applied only if the corresponding `EMAIL_TRIAGE_*` env var is *not* already set. The env file used is `profiles/<name>/.env` if it exists, else the root `.env`.

**New path:** `Settings.load_for_user(user: int | str | None, *, conn=None)` is the entry point every new caller should use instead of `load_for_profile`. `user=None` resolves the global/no-tenant view (env + `data/config.yml` + `profiles/config-local.yml`, no filesystem side effect — used by the scheduler's process-wide reads and the module-level `settings` singleton). A string/int `user` is looked up in `data/app.db`'s `users` table (`users_store.get_user_by_username`/`get_user`); if found, `workspace_dir` becomes `profiles/<user.workspace_slug>/` (same YAML/`.env` cascade as the legacy path, just keyed by the immutable `workspace_slug` instead of a raw profile-name string) and a final overlay is applied from `app_settings_store.apply_to_settings` — **`data/app.db` settings win over env vars and YAML**, a deliberate inversion of the historical "env always wins" rule, required so the admin System Settings UI actually takes effect. If no matching user exists, `load_for_user` transparently falls back to `_load_for_profile_legacy(name)` — the exact original implementation, byte-for-byte — so every existing profile keeps working with zero changes until it's migrated. `Settings.load_for_profile`/`list_profile_names()` remain as deprecated aliases for backward compatibility (auto-rater scripts, `classifier_tester.py`, etc. still call them).

`data/`, `profiles/`, and `.env` are excluded from the Docker build context via `.dockerignore` and are instead bind-mounted at runtime (see `docker-compose.yml`) so they aren't baked into the image. `data/app.db` and `data/secret.key` live in that same bind-mounted directory.

#### User accounts, sessions, and MCP tokens (`appdb.py`, `users_store.py`, `security.py`, `web_auth.py`)

`data/app.db` (raw `sqlite3`, no ORM — same `SCHEMA` tuple + `LATE_COLUMNS` additive-migration pattern as `db.py`) holds `users`, `sessions`, `mcp_tokens`, `integrations`, `app_settings`, and `user_settings`. Bootstrapped automatically at SSE-transport startup (`appdb.init_app_db()` + `users_store.seed_admin()`, both idempotent) — a fresh install gets a `admin`/`password` account with `must_change_password=1`, mirroring `../src/my-meeting-notes`'s bootstrap pattern. Password hashing is stdlib `hashlib.scrypt` (no bcrypt/argon2 dependency); session tokens and MCP tokens are opaque, stored only as a `sha256` hash, with the raw value living in a cookie (session) or shown once at creation (MCP token) — see `security.py`.

Dashboard auth is cookie-based sessions (`web_auth.py::requires_user`/`requires_active_user`/`requires_admin` — Starlette decorators standing in for FastAPI's `Depends`, since this app has neither). `requires_active_user` additionally 409s with `password_change_required` while a user's `must_change_password` flag is set; only `/api/auth/{me,change-password,logout}` use the weaker `requires_user` so a forced user can still act. MCP protocol auth (`/sse`, `/messages/`) is `mcp_server.py::AppAuthMiddleware`, which replaced `MCPTokenAuthMiddleware`: it resolves a bearer token against `data/app.db`'s `mcp_tokens` table first, and only falls back to the legacy `.env`-scraped `EMAIL_TRIAGE_PROFILE_TOKEN` map (`load_token_profile_map`) if no DB match is found — so existing MCP client configs keep working unmodified. Either path sets the same `current_profile` contextvar `get_resources()` already reads, so no changes were needed there. Users self-service their own MCP tokens at `/api/me/mcp-tokens` (list/create/revoke) instead of running `generate_profile_token.py` — that script is still needed for any profile not yet migrated into the DB.

#### Multi-account mailbox integrations (`integrations_store.py`, `account_clients.py`, OAuth)

The historical "exactly one Gmail + one IMAP per profile" limit is gone for DB-backed users: `data/app.db`'s `integrations` table holds one row per connected mailbox (`provider` ∈ `gmail`/`zoho`/`imap`, unique on `(user_id, provider, account_key)` — not `(user_id, provider)` — specifically so two Gmail accounts for one user coexist). Credentials (OAuth tokens, IMAP/SMTP passwords, per-integration OAuth client id/secret) are Fernet-encrypted in `secret_json` via `secretstore.py` (key at `data/secret.key`, auto-generated 0600, or `EMAIL_TRIAGE_SECRET_KEY`).

`GmailClient`/`IMAPClient` gained pluggable credential sources (`credential_source.py`'s `FileTokenSource`/`DbTokenSource`, `mail_auth.py`'s `PasswordMailAuth`/`XOAuth2MailAuth`/`PasswordSmtpAuth`/`XOAuth2SmtpAuth`) — when none is given they fall back to the original `Settings`-based construction byte-for-byte, so the CLI and auto-rater scripts need no changes. `account_clients.py::clients_for_user(conn, user_id, settings, ...)` builds one `AccountClient` per enabled integration row (or falls back to the legacy single-Gmail+single-IMAP pair when the user has zero rows), and is what `mcp_server.py`'s sync engine, `main.py`, and `triage.py::mark_emails_read` all loop over — each of those three has a **dual path**: if `data/app.db` has a user matching the profile name, loop over `account_clients.clients_for_user(...)`; otherwise run the original two-branch Gmail/IMAP construction unchanged. `email_cache`'s `integration_id`/`provider` columns (additive, like every other column in that table) get backfilled by the migration script; new rows get them stamped going forward once a mailbox is DB-backed.

Real Zoho OAuth2 (`oauth_zoho.py`) is delivered as **XOAUTH2 over the existing `IMAPClient`** (`imap_tools.MailBox.xoauth2()`), not a separate Zoho Mail REST client — the pipeline's cache is keyed on the RFC Message-ID, which Zoho's REST search API doesn't expose. `oauth_google.py`/`oauth_zoho.py` each expose `client_for()` (builds an `oauth_flow.OAuthClient` from the admin-configured `google_client_id`/`zoho_client_id` app-level credentials), `fetch_identity()`, and `refresh()` (called by `token_service.py::access_token()`, which adds a per-integration lock + `secret_version` compare-and-swap so a concurrent refresh from two processes doesn't clobber the winner). `oauth_flow.py` owns the provider-agnostic parts: building the authorize URL and a signed, stateless HMAC `state` parameter (`make_state`/`parse_state`) that survives the round trip to the provider and back, since the OAuth callback route (`web_integrations_api.py`) is deliberately unauthenticated — the browser arrives from Google/Zoho with no session cookie guaranteed, so identity is proven by the signed state plus a short-lived nonce cookie instead. Connecting a new OAuth account requires the admin to set `public_base_url` (must be `https://` or `http://localhost`) and the provider's client id/secret in System Settings first — `GET /api/integrations/providers` reports `available: false` with a human-readable reason otherwise.

#### One-time migration (`migrate_to_db.py`)

`python migrate_to_db.py --dry-run` (then for real, no flag) imports the filesystem world into `data/app.db`: global `data/config.yml`/root `.env` → `app_settings`; each real `profiles/<name>/` (has a `.env`, `config.yml`, or `token.json` — the empty phantom `profiles/default/` is skipped) → a `users` row keyed by that exact directory name as `workspace_slug` (so the 400MB+ `email_cache.db` files never move); `token.json` + `google_cli_client.json` → an encrypted `gmail` integration; `EMAIL_TRIAGE_IMAP_LOGIN`/`_PASSWORD` → an encrypted `imap` integration; `EMAIL_TRIAGE_PROFILE_TOKEN` → an `mcp_tokens` row with the *same* raw value (so existing MCP client configs don't need updating). Idempotent, guarded by an `app_settings` marker row (`bootstrap_imported_v1`) — a second run is a no-op. **Non-destructive**: nothing on disk is deleted or modified; `.env`/`config.yml`/`token.json` remain as the rollback path (`rm data/app.db` + revert code). Migrated users get a random temporary password with `must_change_password=1` (printed once in the report) since they never had a login password before (only mail credentials). A fresh `admin` user is always created if `data/app.db` has zero users; `stone` is additionally promoted to admin during import (its `.env` holds this deployment's global LLM config, i.e. it's the de facto operator) — see `DEFAULT_EXTRA_ADMIN_USERNAMES`.

### Ingestion clients (`gmail_client.py`, `imap_client.py`)

Both expose the same shape: `fetch_unread_messages`/`fetch_unread_headers` (metadata-only, headers `Message-ID/From/Subject/Date` + snippet, never downloads bodies), `fetch_full_body`, `mark_as_read`, `search_messages`, `create_draft`/`create_reply_draft`, `send_reply`. In the CLI pipeline (`main.py`), `fetch_full_body` is only called after a message clears Level 0/0.5/1; the MCP server's background sync engine (`mcp_server.py::sync_account`) instead fetches full body upfront for every unread message (skipping the fetch if already cached), since it always persists content regardless of triage outcome. Gmail fetches unread state without marking read by construction (label-based); IMAP explicitly passes `mark_seen=False` everywhere. Gmail metadata fetches use HTTP batching (`_fetch_metadata_batch`, chunks of 100) with a sequential per-message fallback if the batch call fails; `fetch_full_bodies_batch` batches the same way. Both batch methods route every chunk through `GmailClient._throttle_batch_call`, which sleeps as needed to keep at least `_INTER_BATCH_DELAY_SECONDS` (2s) between successive HTTP batch calls **on that client instance**, including across separate top-level calls (not just between chunks within one call) — Gmail counts every sub-request in a batch against the per-user-per-minute quota individually, so without this a large job (e.g. the full-mailbox downloader below) blows through quota and gets `403 rateLimitExceeded` within the first minute; the existing exponential-backoff retry in both methods is a reactive fallback for whatever still slips through, not a substitute for this proactive pacing. IMAP send uses SMTP directly (`smtp_host`/`smtp_port`, falling back to the IMAP login/password if `smtp_login`/`smtp_password` are unset) and appends a copy to the Sent folder afterward.

Both clients accept an optional pluggable auth argument (`GmailClient(credential_source=...)`, `IMAPClient(mail_auth=..., smtp_auth=...)`) so the same class serves both the legacy file/`.env`-backed construction and the new DB-backed multi-account path — see `credential_source.py`/`mail_auth.py` and the "Multi-account mailbox integrations" section above. When omitted, both fall back to their original `Settings`-based behavior exactly as before.

#### Full mailbox archive downloader (manual or nightly, no triage)

Step 1 of a planned local full-archive + embedding search feature (not built yet): a "Download All" button per profile on the dashboard (`POST /api/download_all/start`) triggers `mcp_server.py::full_download_profile` → `full_download_account`, once per account, with the same DB-vs-legacy dual path as `sync_profile` above. Unlike the regular sync engine, this lists **every** message in the mailbox — `GmailClient.list_all_ids()` (no `q` filter, matching Gmail's own "All Mail" scope: everything except Spam/Trash) / `IMAPClient.fetch_all_headers()` (`AND(all=True)`, same INBOX-only scope as the rest of this client) — and persists metadata + body via the same download-phase `upsert_email_metadata` used elsewhere, but **never calls the triage pipeline**, so `triage_level` stays `NULL` for everything it downloads. It's resumable: `db.get_archived_source_ids(account)` (source_ids with a cached `email_body`) lets it skip messages already fully archived on a prior run, so re-clicking after an interruption (or a quota-related partial failure) just continues. It shares the regular sync's per-profile `threading.Lock`/stop-event (`_get_profile_lock`/`_get_stop_event`), so it can't run concurrently with a normal sync for the same profile, and the existing Stop button cancels it too.

Also runs on its own recurring schedule (MCP server, SSE transport only), independent of the regular sync's `scheduler:` block: `download_all_scheduler_loop` in `mcp_server.py`'s `__main__`, gated on `settings.download_all_scheduler.enabled` (default `true`) and firing every `settings.download_all_scheduler.interval_seconds` (default `"24h"` — nightly). Unlike `scheduler_loop`, it *sleeps first* rather than firing immediately on startup, since a full mailbox listing on every container restart would be wasteful; after the first (expensive) backfill, subsequent runs are cheap since already-archived messages are skipped, so nightly just picks up whatever's new. This is process-wide like `scheduler:`, not resolved per-profile.

### CLI output contract (`main.py`)

Default mode emits *only* a raw JSON array to stdout (all logging silenced to `CRITICAL`) so it can be piped into other tooling — never add prints/logs to default-mode paths without gating on `args.human`. `--compact` remaps to short keys (`mid`/`lvl`/`snd`/`sub`/`dt`/`tag`/`sum`) — see `email-triage-engine/references/output_schema.md` for the full field mapping and semantics. `--output <path>` writes the verbose array to disk and prints only a small pointer JSON object to stdout.

### MCP server (`mcp_server.py`)

`RobustFastMCP.call_tool` strips `email_triage__`/`email-triage__` prefixes and fuzzy-matches truncated tool names before dispatch — expect tool names to arrive mangled by some MCP hosts. `get_resources(profile_name)` is the standard entry point for every tool implementation; it re-resolves settings per call (so profile switches take effect without restarting the server).

#### Dashboard API auth and routes (`web_auth.py`, `web_api.py`, `web_integrations_api.py`, `web_static.py`)

The dashboard is a Vite/React SPA (`web/`, see below) rather than server-rendered HTML. `/dashboard` and `/dashboard/logs` are now plain 302 redirects to `/` and `/logs` for old bookmarks. Every dashboard-facing route requires a session (`requires_active_user`) or admin (`requires_admin`) except `/api/auth/login`, the OAuth callback, `/version`, and `/healthz`: `GET /api/status` is scoped to the caller's own profile unless they're an admin passing `?all=1`; `/api/sync/start|stop`/`/api/download_all/start` reject a non-admin targeting anyone but themselves (or `"all"`); `/api/logs`/`/api/logs/stream` are admin-only (the in-memory log ring buffer contains every user's senders/subjects). `web_api.py` owns `/api/auth/*`, `/api/me/*` (including self-service MCP tokens), `/api/users/*` (admin), and `/api/settings`; `web_integrations_api.py` owns `/api/integrations/*` including the OAuth connect flow. `web_static.py::register_spa_route` serves `web/dist` and is registered **last** among `mcp.custom_route` calls (FastMCP gives custom routes registration-order match precedence), so its `/{full_path:path}` catch-all can never shadow `/sse`, `/messages/`, or any `/api/*` route.

`AppAuthMiddleware` (replaced `MCPTokenAuthMiddleware`) guards `/sse` **and** `/messages/` (the latter wasn't guarded before — tool calls execute inside the `GET /sse` request's task, so `/messages/` POSTs were relying on an unguessable session_id alone). It resolves a bearer token against `data/app.db`'s `mcp_tokens` table first, falling back to the legacy `.env`-scraped map (`load_token_profile_map`) only if no DB match exists. A `/messages/` POST that carries no valid token of its own is still allowed through if its `session_id` matches one already recorded in `_session_profiles` — populated by watching the outgoing bytes of that session's own `/sse` connection for the `mcp` SDK's `event: endpoint` line (`mcp/server/sse.py::connect_sse`), which is the only place the SDK ever exposes the session_id it minted, and which never carries the original token forward. This matters because most SSE-based MCP clients only ever authenticate the initial `GET /sse` request, not the follow-up POSTs the SDK's own endpoint URL directs them to — requiring a token on every `/messages/` request (the original design) 401s essentially every real client. The `_session_profiles` entry is removed the moment its owning `/sse` connection closes, so a session can never be reused after the client disconnects.

`fetch_and_process_unread` is **cache-only**: it never calls Gmail/IMAP, it just reads `db.get_unread_emails(account=...)` and renders whatever's currently cached as unread (including a "pending background triage" section for rows that have been downloaded but not yet classified). All live downloading + triaging now happens out-of-band via the background sync engine described below; use `trigger_download` to force a refresh and `get_last_download_time` to check staleness before trusting `fetch_and_process_unread`'s output. `search_emails` is unaffected and still does a live Gmail/IMAP search.

#### Background sync scheduler

Under SSE transport (the only long-running mode — see Docker below), `mcp_server.py`'s `__main__` block runs an `anyio` task group alongside the uvicorn server: a `scheduler_loop` fires `sync_all_profiles()` immediately on startup, then every `settings.scheduler.interval_seconds` (default 15 minutes, gated on `settings.scheduler.enabled`). Under stdio transport the scheduler is a no-op (logged) since `FastMCP.run()` blocks with no task-injection point.

- `sync_all_profiles()` → `sync_profile(name)` for every `list_profile_names()` entry → `sync_account(...)` once per account. `sync_profile` has the same dual DB-vs-legacy path as `Settings.load_for_user`: `mcp_server.py::_db_integration_accounts` looks up a `data/app.db` user matching the profile name and, if found, loops `sync_account` over `account_clients.clients_for_user(...)` (however many Gmail/Zoho/IMAP integrations that user has connected — no longer capped at one of each); if no such user exists it falls back to the *original* two-branch Gmail/IMAP construction unchanged. That legacy branch skips a side entirely (no client construction, no network call) if its identity is still the uninitialized placeholder default (`_PLACEHOLDER_GMAIL_ACCOUNT`/`_PLACEHOLDER_IMAP_LOGIN`) — this matters because `list_profile_names()` always includes `"default"`, so a `profiles/default/` directory that was never actually configured (no `.env`/credentials) would otherwise fail loudly with auth errors on every tick. `_profile_status`/`_dashboard_status` follow the same dual-path shape for read-only status display (`_resolve_account_metadata`, no live client construction), adding an `accounts: [...]` list to the payload while keeping the legacy `gmail`/`imap` keys populated (first matching account of each family) for compatibility with any caller still reading the old fixed-pair shape.
- `sync_account` lists the *complete* live-unread set (unbounded, not capped by `max_per_account`) and reconciles it against `db.get_unread_message_ids(account)` (anything cached-unread but no longer live-unread gets flipped to read via `upsert_email_metadata(..., is_unread=False)` — this is the "did someone read it elsewhere" check). For Gmail specifically, listing goes through `GmailClient.list_unread_ids` (bare `messages.list` pagination, no per-message metadata) plus `mcp_server.py::_resolve_gmail_live_metadata`, which reuses `db.get_known_source_metadata` for internal ids already seen on a prior tick and only calls `_fetch_metadata_batch` for genuinely new ones — otherwise an account with a large persistent backlog would re-fetch metadata for its entire unread set (thousands of messages) every tick and trip Gmail's per-user rate limit. IMAP still uses `fetch_unread_headers` directly (no equivalent metadata cache, since IMAP header fetches aren't rate-limited the same way). From the reconciled live set, up to `scheduler.max_per_account` messages are selected for download+triage, *prioritizing not-yet-triaged messages* (via `db.get_triaged_message_ids`) over whatever the live list's natural (recency) ordering would pick — otherwise a backlog larger than `max_per_account` would have its tail permanently starved, since the same top-N slice would be reselected every tick. Selected messages get full body content downloaded and `_run_tiered_triage` run if not already triaged.
- `sync_profile` is guarded by a per-profile `threading.Lock` (non-blocking `acquire`) shared between the scheduler tick and a manual `trigger_download` call, so the same profile is never synced concurrently — a racing call just gets `{"status": "skipped"}`.
- Gmail's `list_unread_ids` follows `nextPageToken` to return the full unread set (fixed as part of this feature — it used to silently cap at Gmail's default 100-message page); IMAP's `fetch_unread_headers` was already unbounded via `imap_tools`.
- **Auto-mark-read** (opt-in, default off; configured independently per triage level via `auto_mark_read.level_0`/`level_1`/`level_2`, each its own `enabled`/`after_displays`): the last step of `sync_account` builds a `{triage_level: after_displays}` dict from whichever levels have `enabled=True`, then marks matching messages read — both remotely (`client.mark_as_read`) and in the local cache — once a message has been triaged into that level *and* shown to the user via `fetch_and_process_unread` at least that level's `after_displays` times. A level omitted from the dict (i.e. not enabled) is never auto-marked regardless of display count, so e.g. level 0 (noise) can be auto-cleared after one view while level 2 (important) stays fully manual. `fetch_and_process_unread` bumps a per-message `email_cache.display_count` column (`db.increment_display_count`) for every triaged row it actually renders; `db.get_auto_mark_read_candidates(account, thresholds)` is what `sync_account` reads back to find eligible messages per level. Since this only runs from the sync engine (which already holds a live Gmail/IMAP client per tick), the cache-only `fetch_and_process_unread` tool itself never touches the network.

#### Production quality check (`quality_check.py`, nightly "no-look" audit)

A separate, opt-in (`quality_check.enabled`, default off) scheduler under SSE transport: `quality_check_scheduler_loop` in `mcp_server.py`'s `__main__` sleeps until the next occurrence of a configured wall-clock time (`quality_check.hour`/`minute`, default 01:00 UTC) rather than firing on a fixed interval like `scheduler:`/`download_all_scheduler:`, then calls `quality_check.run_quality_check_all_profiles()` and re-arms for the next day. An admin can also trigger a full pass on demand via `POST /api/quality/run-now` (`mcp_server.py::_start_quality_check_now`, a background thread guarded by a single process-wide lock since one pass already loops over every profile/account itself).

For each active DB-backed user with a judge model configured (`quality_check.enabled` too, unless this is a forced manual run — see below), `run_quality_check_all_profiles` resolves a window — the end of that user's last successful run if more recent than 24h ago, else the last 24h (`quality_check.py::_resolve_window_start`) — then calls `run_quality_check_for_user` once per user with the full list of `account_clients.clients_for_user(..., for_triage=True)`. That function pools *every one of the user's accounts'* already-triaged messages into one combined population for the window (`db.get_triaged_messages_in_window`, which accepts a list of account keys — regardless of which stage produced each message's original level: VIP bypass, static blacklist, TEI router, or the LLM) and samples from that combined pool via `_stratified_sample`, which draws `quality_check.sample_rate` independently *within each triage_level group* rather than one flat draw across everything — e.g. 20/50/30 messages at level 0/1/2 at a 10% rate become a 2/5/3 sample, not just "10 random messages" that could by chance land entirely on one level — with a floor of 1 for any level that has at least one message. Sampling is pooled across accounts specifically so a low-volume account doesn't round its own share down to zero every night; the selected sample is then partitioned back by account, and one `quality_check_runs` row is still persisted per account (via `run_quality_check_for_account`, which also accepts an explicit `population`/`sample` to use instead of querying/sampling on its own — the path `run_quality_check_for_user` takes; querying and stratify-sampling within a single account is only the fallback when `run_quality_check_for_account` is called directly, e.g. in tests).

For each sampled message, the judge independently re-derives a final triage level through a **judge** `EmailTriageEngine` — a second engine instance built from a deep-copied `Settings` with `triage_base_url`/`triage_api_key`/`triage_model` and `summary_base_url`/`summary_api_key`/`summary_model` all pointed at `quality_check.judge_base_url`/`judge_api_key`/`judge_model` instead of the account's real models (and `triage.triage_type` forced to `"llm"` even if the account normally routes through the TEI reranker) — running `run_level_1_classification`, then `run_level_1_premium_escalation` only if the judge's own confidence is below `triage.confidence_threshold` (fetching the body live via the account's client only if not already cached; see `_fetch_body_if_possible`). The judge always uses the same prompts.yml/DB-stored system prompts as production (only the model/endpoint differ), and its token spend is captured separately (`_NullTokenSink`) rather than being written into the account's real `token_logs`.

Two metrics come out of each run: **precision/recall/F1** on triage level, computed by `_macro_prf1` as a macro average over levels {0, 1, 2} treating the judge's re-derived level as ground truth and the already-cached production level as the prediction being evaluated (standard shadow-eval methodology — this only needs the judge to independently reach a level, not to know *why* production reached its own); and **summarization quality**, scored only for messages production actually summarized (cached `triage_level == 2` with a non-empty `level_2_summary`) by asking the judge model to grade that production summary 1-10 across accuracy/conciseness/actionability (mirroring `auto_rater_summarizer.py`'s rubric) rather than generating a second summary to diff against, since there's no natural "predicted vs actual" pair for free text. Results are persisted to `data/app.db`'s `quality_check_runs` (one row per account per run — sample/population size, judge model, the three level metrics, summary-quality average/count, status `ok`/`error`/`no_data`) and `quality_check_items` (one row per sampled message, for drill-down). `backfill_quality_check.py` reuses `run_quality_check_for_user` directly with explicit day-by-day historical windows (bypassing `_resolve_window_start`) to retroactively populate N days of trend data. Both this and the admin's "Run now" trigger (`POST /api/quality/run-now` → `run_quality_check_all_profiles(force=True)`) intentionally bypass the `quality_check.enabled` check — that flag only gates the *automatic nightly schedule*, not an explicit manual invocation — while still requiring a judge base_url/model to be configured, since there's nothing to compare against otherwise.

`web_quality_api.py` exposes admin-only (`@requires_admin`) read routes — `GET /api/quality/trend?days=N` (per-day metrics zero-filled across the range, each a sample-size-weighted average across every account's run that landed that day, plus `run_count`/`error_count`/`no_data_count` so "nothing ran" is visibly distinct from "it ran and failed") and `GET /api/quality/runs?days=N` (recent per-account run rows joined to username, for API/DB-level drill-down — not currently rendered anywhere in the SPA, which only shows the day-grouped view) — the trend rendered by the SPA's `/admin/quality` page (`AdminQualityPage.tsx`, a day-grouped table + `QualityTrendChart.tsx`, a hand-rolled SVG line chart with a hover crosshair/tooltip and direct endpoint labels, matching the no-library style of `TokenUsageChart.tsx`). The judge model/endpoint and schedule are configured like every other global setting, under System Settings → "Quality check" (`app_settings_store.py`'s `RUNTIME_KEYS`, all global/admin-only — this feature is disabled per-user opt-out, not per-user configurable, since judge spend is an operator cost decision).

### Dashboard SPA (`web/`)

A Vite + React + TypeScript single-page app, replacing the old inline-HTML-in-Python dashboard. Plain `fetch`-based API client (`web/src/lib/api.ts`) + hooks (no react-query), hand-rolled CSS (no Tailwind) — kept deliberately minimal-dependency. `web/src/routes/guards.tsx` (`RequireAuth`/`RequirePasswordChanged`/`RequireAdmin`) and `web/src/hooks/useAuth.tsx` mirror the pattern from `../src/my-meeting-notes`. Routes: `/login`, `/change-password` (forced-change wall), `/` (dashboard), `/logs` (admin-only), `/settings/{integrations,mcp,password}`, `/admin/{users,settings}`. OAuth connect is a full-page redirect (`window.location.href = authorize_url`), not a popup — the callback lands back on `/settings/integrations?connected=<provider>` or `?error=...`.

Built with `npm run build` (in `web/`) to `web/dist`, served by `web_static.py` at runtime; `npm run typecheck` runs `tsc -b --noEmit`. Not checked into git (`web/dist/`, `web/node_modules/` are gitignored/dockerignored) — the Dockerfile builds it fresh in a `node:20-alpine` stage and copies `web/dist` into the Python runtime image (see `EMAIL_TRIAGE_WEB_DIST` below). No frontend test suite exists yet (Vitest was scoped for this but not added) — verification so far is the Python-side integration test (`tests/test_web_static.py`) plus a manual end-to-end smoke test (build → serve → login → API calls) during development.

### Auto Rater suite

Offline benchmarking pipeline independent of the live CLI/MCP paths: `auto_rater_downloader.py` snapshots unread mail to disk, `auto_rater_config.yml` defines named model/routing configurations to sweep, `auto_rater_runner.py` executes the full triage pipeline (its own inline copy, not calling `main.py`) per configuration and writes results per-config, `auto_rater_triage.py` scores classification accuracy against a human-labeled gold set, `auto_rater_summarizer.py` LLM-judges summary quality. `classifier_tester.py` is a separate standalone tool that generates an HTML comparison report across classifier configs on a dataset.

## Configuration reference

- `EMAIL_TRIAGE_*` env vars (see `.env.example`) take precedence over `data/config.yml`/profile YAML — **except** for a DB-backed user (one that exists in `data/app.db`, i.e. has been through `migrate_to_db.py`), where `app_settings`/`user_settings` rows win over both env vars and YAML. This inversion only applies once a user is DB-backed; unmigrated profiles keep the original env-wins-over-YAML behavior untouched.
- LLM endpoints are decoupled per stage: `EMAIL_TRIAGE_TRIAGE_BASE_URL`/`_API_KEY` for Level 1, `EMAIL_TRIAGE_SUMMARY_BASE_URL`/`_API_KEY` for Level 2 (and premium escalation) — these can point at different proxies/providers.
- Model *names* (`triage_model`, `summary_model`) are set in `data/config.yml` under `llm:` (legacy) or as `app_settings` rows editable from Admin → System Settings (DB-backed), not in `.env`.
- Background sync scheduler (MCP server, SSE transport only): `scheduler:` block in `data/config.yml` (`enabled`, `interval` — a duration string like `"15m"`/`"1h"` parsed by `config.py::parse_duration`, `max_per_account`, `days`), or `EMAIL_TRIAGE_SCHEDULER_ENABLED`/`_INTERVAL`/`_MAX_PER_ACCOUNT`/`_DAYS` env vars. This is process-wide (one scheduler loop syncs every profile per tick), so it's read from the global/default `settings` singleton, not resolved per-profile.
- Full-mailbox download scheduler (MCP server, SSE transport only): `download_all_scheduler:` block in `data/config.yml` (`enabled`, default `true`; `interval`, default `"24h"`), or `EMAIL_TRIAGE_DOWNLOAD_ALL_SCHEDULER_ENABLED`/`_INTERVAL` env vars. Also process-wide, independent of `scheduler:`.
- Auto-mark-read (opt-in, default off): `auto_mark_read:` block in `data/config.yml`, with `level_0`/`level_1`/`level_2` each independently configured (`enabled`, `after_displays` — how many times `fetch_and_process_unread` must have shown a message triaged into that level before it's auto-marked read), or `EMAIL_TRIAGE_AUTO_MARK_READ_LEVEL_{0,1,2}_ENABLED`/`_AFTER_DISPLAYS` env vars. Unlike `scheduler:`, this is resolved per-profile (read from `settings_instance` inside `sync_account`), so different profiles — and different levels within a profile — can enable it independently. See "Auto-mark-read" under Background sync scheduler above.
- Production quality check (MCP server, SSE transport only; opt-in, default off): `quality_check:` block in `data/config.yml` (`enabled`, `hour`/`minute` — daily run time, default 01:00 UTC; `sample_rate`, default `0.10`; `judge_base_url`/`judge_model`/`judge_api_key` — a separate LLM endpoint used only to shadow-evaluate, not to make real triage decisions), or the matching `EMAIL_TRIAGE_QUALITY_CHECK_*` env vars. Process-wide/admin-only like `scheduler:`, editable from Admin → System Settings → "Quality check". See "Production quality check" under MCP server above.
- Sender lists (`whitelist_vip_senders`/`whitelist_domains`/`blacklist_keywords`/`blacklist_senders`) are, for a DB-backed user, editable per-user (`user_settings`, `triage.confidence_threshold` too) rather than global — these are the only `RUNTIME_KEYS` marked `user_overridable=True` in `app_settings_store.py`; everything else (models, scheduler, auto-mark-read) is global/admin-only.
- New env vars for the DB-backed dashboard/auth layer: `EMAIL_TRIAGE_SECRET_KEY` (Fernet key for `data/app.db` credential encryption, auto-generated at `data/secret.key` if unset), `EMAIL_TRIAGE_SESSION_COOKIE_SECURE`, `EMAIL_TRIAGE_PUBLIC_BASE_URL` (required before connecting any OAuth account — see "Multi-account mailbox integrations" above; also settable as the `public_base_url` admin setting), `EMAIL_TRIAGE_WEB_DIST` (where the built SPA lives, default `web/dist`), `EMAIL_TRIAGE_SPA_REDIRECT_BASE` (dev-only, OAuth-callback redirect target when running `npm run dev`), `EMAIL_TRIAGE_SESSION_TTL_HOURS`, `EMAIL_TRIAGE_PASSWORD_MIN_LENGTH`. See `.env.example`.
- `email-triage-engine/SKILL.md` documents the CLI's JSON output contract for agent consumers — keep it in sync with any change to `main.py`'s output schema.
